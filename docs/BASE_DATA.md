# SmartOffice 基础数据与初始化清单

- 文档版本：v1.0
- 基线日期：2026-11-25
- 适用范围：单一企业、MySQL 唯一持久化版本

## 1. 目的与边界

正式初始化用于**已完成数据库迁移、尚未写入任何业务数据的新系统**。它一次性写入正式会议室、总部 3D 空间、初始组织、预约规则、审批流程和会务目录，不包含演示预约、演示工位或历史测试数据。

初始化不是日常升级工具：

- 仅允许空业务库执行；任一核心业务集合或总部 3D 相关表已有记录都会拒绝。
- 核心状态与总部 3D 在同一个 MySQL 事务中提交，失败整体回滚。
- 重复执行会拒绝，不覆盖、不修补、不合并现有业务数据。
- 已有业务库升级只执行备份、新增迁移和应用发布，不得执行 `db:init`。
- 初始化后，MySQL 是运行时唯一权威；修改页面中的资源、规则或房间资料不会回写初始化 JSON。

## 2. 版本化输入与写入位置

| 基础数据 | 版本化来源 | 运行时写入位置 | 后续维护方式 |
|---|---|---|---|
| 28 间会议室 | `server/data/meeting-rooms.json` | `office_state.resources` | 空间资源库、受控台账导入 |
| 总部楼栋、楼层、空间与几何 | `server/data/hq3d-floorplan.json` | `hq3d_building`、`hq3d_floor`、`hq3d_room` | 总部 3D 导入、房间资料和维护页面 |
| 角色、初始成员、部门 | `constants.ts` | `office_state` 对应集合 | 权限集、成员和部门管理 |
| 预约规则 | `constants.ts` + `server/bootstrap.ts` | `office_state.ruleVersions` | 数据中心规则配置，追加版本 |
| 默认流程与动态审批规则 | `constants.ts`、`utils/approvalPolicy.ts` | `workflowVersions`、`approvalRuleSetVersions` | 流程配置，追加不可变版本 |
| 会务目录与默认责任区 | `constants.ts`、`server/serviceDomain.ts` | `serviceCatalog`、`serviceAreas` 等 | 会务服务配置与责任区维护 |
| 空业务事实 | `server/bootstrap.ts` | 预约、工单、签到、通知、设备等集合 | 系统运行后产生 |

## 3. 正式会议室

基线来自 2026-11-10 房间台账的需求口径，共 **28 间会议室**：

| 分类 | 数量 | 初始化行为 |
|---|---:|---|
| 可开放会议室 | 18 | `AVAILABLE`，容量使用源台账座位数 |
| 待核验会议室 | 10 | `PENDING`，不开放正常预约 |
| 合计 | 28 | 全部为 `ROOM`，ID、code 和名称均唯一 |

- 楼层覆盖主楼 1、2、3、5、7、8、11、14、16、19 层。
- 10 间待核验会议室的容量仅为满足资源分类规则的技术占位，**不是已签字容量**；须由管理员或责任方核定后再调整状态。
- 不初始化旧演示资源 `r1`、`r2`、`d1`。
- 不初始化任何预约、审批、签到、工单或通知。
- 新空间或总部 3D 房间不会因初始化自动成为可预约资源；可预约性仍以正式资源台账、显式映射和实时规则为准。

## 4. 总部 3D 与办公室类空间

### 4.1 楼栋与楼层

| 楼栋 | 楼层数 | 空间数 | 逐层空间数 |
|---|---:|---:|---|
| 主楼 `main` | 20 | 332 | 15、34、15、23、16、9、14、9、22、6、20、22、7、18、22、14、20、19、18、9 |
| 南配楼 `annex` | 4 | 95 | 11、19、28、37 |
| 合计 | 24 | 427 | 427 个显式且全局唯一 UID |

空间记录包含类别、名称、房号、部门、使用人、备注和归一化几何。UID 是稳定身份，不能按名称、楼层顺序或数组位置重新生成。

### 4.2 办公室类口径

办公室监控只统计 `office`、`open`、`exec` 三类，共 **203 个办公室类空间**：

| 类别 | 数量 | 含义 |
|---|---:|---|
| `office` | 171 | 独立办公室 |
| `open` | 20 | 开放办公区，不是逐工位台账 |
| `exec` | 12 | 高管办公室 |

按静态初始化基线及当前状态派生规则计算：

- 已分配 143：登记了使用人或部门。
- 空置 2：资料明确标记空置。
- 未登记 58：没有分配或明确空置信息。

这些数量只是首次初始化输入的静态派生结果，不是当前业务库实时结果，也不是门禁、传感器或现场实测人数。办公室分配事实来自 `hq3d_room` 及后续 `hq3d_room_profile` 覆盖，没有独立的办公室分配表或逐工位初始化清单。

初始 JSON 不携带平方米字段；楼层总面积和房间面积分别由 `hq3d_floor.area_total` 与 `hq3d_room_profile.area_sqm` 维护，首次初始化为空。

## 5. 初始组织与权限

### 5.1 七个角色

| 角色 ID | 名称 | 默认职责 |
|---|---|---|
| `SYSTEM_ADMIN` | 系统管理员 | 系统配置、运维、最终核准；默认可查看两类监控 |
| `APPROVAL_ADMIN` | 审批负责人 | 资源申请业务审核 |
| `EMPLOYEE` | 正式员工 | 申请和使用公共资源 |
| `SECURITY_ADMIN` | 保密管理员 | 涉密白名单、授权和保密审批 |
| `SERVICE_COORDINATOR` | 会务协调员 | 会务执行与异常处理 |
| `FRONT_DESK` | 前台人员 | 现场签到、巡查和人工释放 |
| `AUDITOR` | 审计员 | 按授权范围查询审计与运行证据 |

默认角色均不携带额外 `monitoringScopes`，因此除系统管理员外，会议室和办公室监控默认都不授权。后续须由管理员按职责分别授权。

### 5.2 三个初始成员与七个部门节点

- 成员 ID `1`：超级管理员，角色 `SYSTEM_ADMIN`。
- 成员 ID `2`：审批负责人，角色 `APPROVAL_ADMIN`。
- 成员 ID `3`：李员工，角色 `EMPLOYEE`。
- 部门：集团总部、信息技术部、架构组、运维组、行政部、市场部、销售部。

初始成员只是内部业务档案，不是可直接使用的生产登录凭证，也不会自动创建 OIDC 身份。投产前应由管理员核对真实姓名、部门、联系方式、角色和启用状态，再按部署手册绑定企业身份；不需要的初始成员应按正式维护流程停用或调整，不能共享账号。

| 部门每日净预约额度 | 240 分钟 |
| 专属资源申请提前开放时间 | 24 小时 |
| 普通预约取消截止 | 开始前 30 分钟 |
| 重服务预约取消截止 | 开始前 120 分钟 |

| 签到提醒 | 开始后 10 分钟 |

## 7. 默认审批流程

默认流程版本为：**行政预审（审批负责人）→ 最终核准（系统管理员）**。

初始化还会生成重要会议、涉密会议和连续长期预约所需流程版本，并写入 5 条动态规则：

1. 涉密会议保密审批。
2. 重要会议强化审批。
3. 连续超过 3 天预约审批。
4. 专属资源临时使用审批。
5. 重服务资源协调审批。

普通预约未命中特殊规则时自动核准。审批流程和规则集均采用版本化设计，新申请使用最新发布版本，在途申请保留提交时冻结的版本。

## 8. 会务目录与责任区

初始化 13 类会务目录：茶水、视频会议保障、引导与标识、现场安保、其他会务、车辆、桌牌、桌椅、饮用水、文具、迎宾、值守和礼堂专项服务。

系统创建 `area-default` 默认会务责任区，初始覆盖全部 28 间会议室。后续自定义责任区只接管明确分配的资源，默认责任区继续承载未分配资源，避免会务工单失去责任范围。

## 9. 初始化为空的其他业务集合

预约、通知、审批代理、工单、资源导入批次、涉密白名单与授权、访问授权、班次、巡查、签到、使用事实、申诉、门口屏、异常处理、组织同步批次、外部回调、外部补偿和集成投递均为空。

`INITIAL_BOOKINGS` 固定为空。不得把历史预约、测试通知、演示身份、演示工位或真实数据库备份混入新系统初始化输入。

## 10. 命令分工

```bash
# 新系统：迁移完成后，仅在空业务库执行一次
npm run db:init

# 演示/隔离测试：3条演示资源，不含正式28间会议室
npm run db:seed

# 既有总部3D布局维护工具：UPSERT并差异软停用，不是空库保护初始化
npm run db:seed:hq3d
```

`db:seed` 继续服务演示和现有测试夹具；`db:seed:hq3d` 会更新现有布局，不能把它当作已有业务库的无差别升级命令。新部署统一使用 `db:init`，具体顺序见 [系统部署手册](DEPLOYMENT.md)。
